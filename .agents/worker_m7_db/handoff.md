## 2. Logic Chain

1. Starting from single-tenant database architecture where 13 tables lacked RLS and tables had single-tenant unique constraints, we implemented the multi-tenant architecture designed in `explorer_m7_db/handoff.md`.
2. Creating `public.sekolah` and seeding default school `SMA Nizamudin` (`a0000000-0000-0000-0000-000000000001`) establishes the root tenant entity with zero downtime for existing data.
3. Adding `sekolah_id` and backfilling with the default school ID ensures 100% data integrity with no orphan records.
4. Setting `NOT NULL` on 16 tables enforces multi-tenant integrity at the schema level, while keeping `users.sekolah_id` nullable allows global platform administrators (`Superadmin`).
5. Replacing single-tenant unique constraints with composite constraints (`sekolah_id, ...`) enables independent school data management (e.g. multiple schools having identical settings keys or piket days).
6. Creating composite ascending indexes optimizes subsequent Milestone 7.4 ascending chronological sorting requirements.
7. Enabling RLS and security helper functions enforces database-level tenant isolation, confirmed by live query testing where non-existent school queries return 0 rows.
8. Generating TypeScript definitions directly from Supabase ensures strict type safety across all frontend components.

## 3. Caveats

1. **Client Header & Session Passing**: RLS helper functions inspect JWT claims, session settings, and PostgREST request headers (`x-sekolah-id` and `x-user-role`). Downstream workers in M7.2/M7.3 must ensure the frontend passes the active school ID when querying Supabase for non-superadmin users.
2. **Pengaturan Upsert Conflict Target**: Unique constraint on `pengaturan` is now `(sekolah_id, key)`. Any `upsert` calls on `pengaturan` should target `sekolah_id,key`.
3. **Legacy Single Tenant**: SMA Nizamudin data is preserved under `a0000000-0000-0000-0000-000000000001`. Newly registered schools by Superadmin will receive distinct UUIDs.
